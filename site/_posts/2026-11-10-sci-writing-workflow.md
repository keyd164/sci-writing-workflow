写论文最难的部分，往往不是想清楚，也不是英文，而是**说不清哪个数字是对的**。

初稿里写"约 0.31"，结果文件里是 0.309，图注里写 0.3，补充材料里又是 0.310。三个版本都像是真的，没有一个能立刻说清它是从哪个脚本、哪个筛选条件、哪次运行里来的。返修时编辑要求核对某个数字，你把三个文件翻一遍，最后靠"应该是这个"定了一个。

我把这类现象归结为三个反复出现的问题，然后用一套技能把它们逐个挡在流程之外。这篇文章讲这套工作流是怎么设计的、为什么这么设计，以及它不解决什么。

## 一、三个反复出现的问题

**问题一：数字漂移。** 同一指标在不同位置出现不同值，原因通常是不同轮次的输出混在一起：主模型改了，敏感性分析没重跑；换了样本口径，摘要忘了同步。人的注意力放在句子通不通顺上，很难同时盯住十七个数字。

**问题二：结论先于证据。** 摘要和引言通常最早写，因为它们"反正最后会改"。但一旦写了"本研究首次量化了某类健康负担"，后面的结果就会不自觉地往这个说法上靠。等到审稿人问"你的证据支持'首次'吗"，才发现这句话从来没有对应的结果。

**问题三：语言层污染科学层。** 润色是最容易被当成"纯技术活"的一步。把 `was associated with` 改成 `drives`，读起来更有力，但关联性结论被悄悄改写成了因果结论。这类改动不会报错，只会让整篇文章的可辩护性下降一个等级。

三个问题有共同点：**出错的位置和发现问题的位置不在一起**。数字错在结果文件，暴露在正文里；结论错在摘要，暴露在审稿意见里。只要写作文本是一整段不可拆的东西，你就只能靠肉眼在几千字里找不一致。

## 二、解法：把状态写进文件，而不是留在脑子里

这套工作流的第一步不是写作，而是建立一套登记册——项目根目录下的 `.paper/`，共 12 个 YAML 文件：

| 文件 | 管什么 |
|---|---|
| `paper.yml` | 题目、研究问题、目标期刊 |
| `workflow.yml` | 阶段与六个门的状态 |
| `claims.yml` | 每条结论的强度与禁止措辞 |
| `results.yml` | 每个数字的来源文件、定位、核验状态 |
| `methods.yml` | 每个模型的定义、样本、必现句子 |
| `decisions.yml` | 已锁定的方法学与写作决策 |
| `terminology.yml` | 术语与数字格式 |
| `references.yml` | 文献条目与三层核验状态 |
| `figures.yml` / `tables.yml` | 图表与证据的绑定 |
| `journal.yml` | 目标期刊规则与核验状态 |
| `changelog.yml` | 实质修改记录 |

关键不在"多写几个文件"，而在两条硬规则：

1. **没有 R-id 的数字，不许进正文。** 每个数字在 `results.yml` 里有一条记录，写清来源文件、行列表位、模型、样本、单位、核验状态。
2. **结论必须标强度。** `association`、`counterfactual`、`scenario`、`descriptive`、`interpretation` 五类分开记，每一类对应一组允许和禁止的措辞。

第一条挡住数字漂移：正文里的每个值都能回溯到一份具体文件，核验过的标 `verified: true`，找不到来源的进"不得进入正文"清单，没有例外。

第二条挡住结论先行：写摘要时不是凭记忆措辞，而是查 `claims.yml` 里 C01 的强度，看它允许用哪个动词。

还有一条容易被忽略的红线：**旧稿数值不得反向填充登记册**。历史稿件里的数字只能被记为"冲突"，不能作为来源。否则登记册会变成"把所有出现过的值都收集起来"的垃圾桶，失去唯一事实来源的意义。

## 三、六个门：把批准权留给作者

登记册解决了"记录"问题，但没解决"谁来决定能不能往下走"。所以流程被切成六个阶段，每个阶段末尾有一道门：

```
清点建档 → 架构 ─G1→ 证据锁定 ─G2→ 起草 → 对齐 ─G3→ 语言层
        → 模拟审稿 ─G4→ 修订 → 期刊适配 → 投稿审计 ─G5→ 提交授权 ─G6
```

| 门 | 它实际拦住的事 |
|---|---|
| G1 架构批准 | 摘要预写了没有数据支持的结论；四个独立分析被拼成一篇 |
| G2 证据锁定 | 正文数字与输出文件对不上；旧稿数值倒灌进登记册 |
| G3 对齐批准 | Results 出现 Methods 从未定义的模型；样本数两处不一致 |
| G4 意见处置 | AI 自己改稿、作者没看过意见；拒绝了意见却写进回复信 |
| G5 投稿审计 | 字数超限、声明缺项、引用编号断裂 |
| G6 提交授权 | 未经确认就对外提交 |

这里有一个刻意的设计：**门只能由作者批准**。模块可以判断"数字是否能追溯到文件"，但不能判断"这个结论是否值得发表"。所以每个门的状态字段只能由人来改，脚本只做只读报告。

配套的 `check_gates.py` 输出当前卡在哪个阶段、哪些门还没批，并且在输出里明确写着"退出码 0 不代表批准"。这句话不是免责声明，是设计意图：工具负责报告事实，判断留给作者。

## 四、未批准不等于停工

如果严格按"没批准就不许动"，流程会陷入死锁：G2 没批，就不能核验数字？可核验正是批准的前提。

所以门控的边界是**下游产出**，不是**准备工作**。未批准时允许做：核验来源、列出冲突、准备候选方案、写审计报告；不允许做的是：正式起草正文、冻结待提交版本、对外提交。

这条规则看起来是细节，实际上决定了这套流程能不能用。过于宽松，门形同虚设；过于严格，人会绕开流程。

## 五、19 个技能怎么分工

仓库里共有 18 个自写技能加 1 个第三方技能，按职责分四组：

**第一组：定证据链。** `paper-bootstrap` 扫描项目、建登记册、标冲突；`scientific-architecture` 做问题—缺口—贡献—主张—证据的映射；`evidence-lock` 把每个数字绑到来源文件和哈希；`statistical-results-lock` 核对单位、区间、模型口径；`causal-inference-audit` 与 `climate-counterfactual-audit` 检查推断边界与反事实构造。

这一组里，前两个负责"写什么"，后四个负责"凭什么"。它们大多是只读的，发现问题只出清单和补丁建议，不直接改登记册——改登记册要经过 `evidence-lock`，因为它是唯一有权核实并写入的模块。

**第二组：写正文。** `evidence-drafting` 按 Evidence → Claim → Paragraph → Section 的顺序写，Results 每段只做四件事：发现、量级、不确定性、比较。`methods-results-alignment` 做双向对照：Results 有而 Methods 无的模型是高危项，一律算阻塞。

**第三组：处理语言。** `scientific-prose` 校准学科语气、去模板化句式与过度强调；`anti-defensive-writing` 去掉重复辩解与习惯性谦辞；`lieflat-less-ai-tone` 按编号白名单处理 AI 痕迹。三者必须在 G3 之后运行，且按固定顺序衔接。

**第四组：收尾。** `figure-planner` 规划图与 panel 的证据绑定；`figure-legend` 写图注并去 Methods 重复；`citation-verifier` 做本地、身份、支持三层核验；`reviewer-red-team` 用四个视角模拟审稿，只评论不改稿；`rebuttal-response` 把意见拆成子问题、决策和实际改稿位置；`journal-adapter` 按目标期刊调整呈现；`submission-audit` 做最后的 pass/fail 全项检查。

技能数量看着多，但入口只有一个：`paper-workflow`。用户说"写 Methods""检查方法结果一致吗""这篇会被怎么批"，总控按现状选模块，不需要记名字。

## 六、三个我认为最值得坚持的取舍

**第一，语言层必须晚于科学层。** 先润色再核数字，会让每一轮润色都变成潜在的漂移源。流程强制 G3 之后才允许语言层运行，并且要求语言层输出一句"本层未改动任何数字与结论"。这句话最容易被随手写上，但一旦真的改了什么，它就成了伪证——所以配套要求是：改动必须逐条注明是哪个检查项、改了哪一行。

**第二，去 AI 味不做同义词替换。** 市面上不少"humanize"工具做的是同义词替换，把 `associated with` 换成 `linked to`。这在科研写作里是负收益：改变不了文风，还会破坏术语一致性。所以语言层采用白名单：只有命中具体规则才动，没命中的句子逐字保留。真正的 AI 味来自模板化句式（连续四个 "We assessed… We calculated…"）和过度总结（"These findings collectively demonstrate that…"），而不是某几个词。

**第三，不确定性按类型分开命名。** 系数置信区间、bootstrap 区间、模型间离散度、情景范围是四种东西，合成一个"总不确定性"会让读者误读成预测区间。流程要求在登记册和图注里分别命名，并且不允许把模型离散度写成预测区间。这条在返修阶段价值最大：审稿人常问"误差线是 CI、SD 还是模型范围"，答案在 `figures.yml` 里写着，不需要回头翻脚本。

## 七、怎么开始

不必一次建满 12 个文件。最小可用集合是四个：`paper.yml`、`workflow.yml`、`claims.yml`、`results.yml`，先把"写什么"和"数字从哪来"管住，图表和引用在对应阶段再加。

装好技能后，第一句话可以这么说：

```text
继续 my-paper 的论文工作。先跑 paper-bootstrap，清点现有稿件、结果和图表，
建立 .paper/ 登记册，把发现的冲突列成清单给我确认。
```

之后要做的检查，用状态报告看进度：

```bash
python skills/paper-workflow/scripts/check_gates.py /path/to/my-paper
```

它会告诉你当前第一个未完成的阶段、哪些门还没批，以及"未批准时允许做什么"。

## 八、它不解决什么

写清楚边界比写清楚功能更重要：

- **依赖登记册质量。** 登记册本身错了，后面所有检查都会一致地错。它拦数字漂移，不拦科学判断错误。
- **不替代领域专家。** 两个审计技能只做边界检查，不能判断你的识别策略在该领域是否站得住。
- **期刊规则会过期。** `journal.yml` 里的 `verified` 带核验日期，字数、图表限制投稿前必须重新确认。
- **对中文期刊适配较弱。** 当前模板假设英文稿件为主，中文期刊的结构与引用规范需要自己补。
- **不做投稿事务。** 不代替投稿平台，不处理版权与署名协议，实际提交必须由作者完成。

这套流程的适用对象是有多个分析、多个图表、要投英文期刊、还会返修的稿件。三千字的短文用它，流程成本明显高于收益。

## 九、仓库与来源

仓库名 `sci-writing-workflow`，包含 18 个自写技能与 1 个第三方技能、12 个登记册模板、四篇文档（门控设计、登记册规则、设计取舍、来源授权）。许可证 MIT。

目录结构：

```
skills/                 18 个技能，各自含 SKILL.md
skills/paper-workflow/  模块契约、来源整合、语言层组合契约、段落证据计划、check_gates.py
templates/paper/        12 个登记册模板
docs/                   门控、登记册、设计取舍、来源与授权
third_party/            lieflat-less-ai-tone（MIT，保留原 LICENSE）
```

其中 `lieflat-less-ai-tone` 是第三方技能，按原授权整份存放；`scientific-prose`、`figure-legend`、`anti-defensive-writing` 的方法骨架参考了若干开源写作技能，规则与措辞全部重写，来源与取舍写在 `docs/attribution.md` 里。上游作者关于语料规模与区分度的描述是他们的报告，我没有独立复核，也不建议当作已验证结论引用。

如果你的论文也遇到过"三个文件三个值"的时刻，这套流程可能值得试一次。不用全装，先从四个登记册开始，把数字管住——那一步的收益最直接。

## 十、写在最后

这套流程最初只是为一篇具体的稿子搭的脚手架。写作过程里反复被数字和措辞绊住，才把能想到的检查一条条写进文件；如今它看起来像一套方法论，其实更像那次返修留下的疤痕。所以要谢的是审稿人和同行：他们的意见把"我以为写清楚了"一句句拆开，逼出了这些门控；也谢谢愿意读到这里的你，如果哪条规则让你觉得多余或过严，多半是我把某个具体场景当成了普遍情况。

不足也很清楚。登记册的维护成本不低，中断一段时间再捡起来，得先重读一遍自己的记录；规则写得比实际执行更严，我自己也绕过几次；十几个技能里，有几个只在一个项目、一种研究设计上跑过，换到别的领域未必成立。这些不是免责声明，而是希望被具体指出的地方——哪条规则是真需要，哪条只是我当时怕出错。仓库和文章都还会改，欢迎拿你自己的稿子试一遍，把不顺手的地方告诉我。
