# 工作流：六个门控与三种产出边界

这套流程的核心不是"让 AI 帮你写论文"，而是把写作拆成**可核对的状态机**：每个阶段产出一份能被作者审阅的东西，作者批准后状态才向前推进。所有限制都写在 `.paper/workflow.yml` 里，模块只读状态、不自己改状态。

## 一张图看懂

```
清点建档  paper-bootstrap
   ↓
架构     scientific-architecture  ──G1──▶  主张有了证据指纹
   ↓
锁定     evidence-lock            ──G2──▶  每个数字都有来源
   ↓
起草     evidence-drafting
   ↓
对齐     methods-results-alignment ──G3──▶  方法与结果互相覆盖
   ↓
语言     scientific-prose + anti-defensive-writing + lieflat-less-ai-tone
   ↓
评审     reviewer-red-team         ──G4──▶  作者逐条决定接受哪些意见
   ↓
修订     evidence-drafting（revision 模式）
   ↓
适配     journal-adapter → submission-audit ──G5──▶  冻结待提交版本
   ↓
提交     用户明确授权              ──G6──▶  实际对外提交
```

## 每个门在拦什么

| 门 | 拦住的典型事故 | 通过条件 |
|---|---|---|
| G1 | 摘要先写了没有数据支持的结论；四个分析拼成一篇 | 每个 Q 有 C-id，每个 C-id 有 R-id 或标 planned |
| G2 | 正文数字与输出文件对不上；旧稿数字倒灌进登记册 | 所有进入正文的数字 `verified: true`，找不到来源的进"不得进入正文"清单 |
| G3 | Results 出现 Methods 没定义过的模型；样本数两处不一致 | 双向对照表无 `results_only`、无样本数冲突 |
| G4 | AI 直接改稿，作者没看过意见；拒绝了意见却写进回复 | 每条意见有 accept/reject/defer 决定与对应改稿位置 |
| G5 | 字数超限、声明缺项、引用编号断裂 | blockers 清零 |
| G6 | 未经确认就投稿或对外发布 | 用户明确授权 |

## 三类产出的边界

写作系统最容易混淆的三件事，这里明确分开：

1. **科学内容**（主张、数字、模型、结论强度）——只有 `evidence-drafting`、`evidence-lock` 可以动，且必须受 claims/decisions 约束。
2. **语言表达**（句式、语气、术语一致性）——`scientific-prose` 等语言层模块可以动，但不得改变数字与结论，且必须在 G3 之后。
3. **呈现约束**（字数、结构、引用风格、图表数量）——`journal-adapter` 可以动，但期刊规则必须来自官方指南并标 `verified`，不得凭记忆填写。

任何模块越界，都属于流程故障，而不是"灵活处理"。

## 未批准的门不等于停工

未批准只阻止**下游正式产出**，不阻止为审批做的准备工作：核验来源、列出冲突、准备候选方案、写审计报告。这条规则的意义在于避免两种极端：既不能因为"还没批准"就拒绝核对证据，也不能因为"反正只是准备"就悄悄产出正文。

## 报告与追溯

每次实质检查输出一份报告，写清：所审输入的路径、SHA256、核验时间、发现的问题、覆盖缺口。输入一变，受影响的结论就要重核，不能沿用旧报告。报告默认放在项目 `audits/` 下，按日期与主题命名。
